# Design Notes

## 1. Concurrency: atomicity, cost, and multiple processes

In my implementation, `RateLimiter` uses a single `threading.Lock`. `check()` acquires it once and holds it for the whole decision. While holding the lock it reads the clock, removes expired timestamps (Policy A) or refills the bucket (Policy B), decides whether to accept, updates the per-key state, and increments `total_allowed` or `total_rejected`. All of these steps happen inside one critical section, so two threads can never both see "one slot left" and both accept. A request's decision and its counter update are therefore never separated. New `(client_id, endpoint)` entries are also created inside the lock, so two threads cannot create duplicate state for the same key. `stats()` takes the same lock, which means it always reads a consistent snapshot: no request can be decided without also being counted, and `active_keys` matches the stored state. The policy methods do not acquire the lock again, because `threading.Lock` is not re-entrant and doing so would deadlock. Reading the clock inside the lock also keeps the timestamps in each sliding-window deque in increasing order, and the eviction loop depends on that.

The cost of this approach is that one global lock serializes every request, even for unrelated clients and endpoints. As traffic grows, threads spend more time waiting on the lock, and the work done inside it (for example, evicting old timestamps in Policy A) adds to that wait. Memory also grows: Policy A stores up to `limit` timestamps per key, and idle keys are never removed. To reduce this cost I would use lock striping. Keys would be split into N shards by `hash(key) % N`, and each shard would have its own dictionary, lock and counters, so clients in different shards no longer block each other. `stats()` would add up the shard counters, acquiring the shard locks in a fixed order whenever an exact snapshot is required. I would also add TTL-based cleanup for idle keys. Where memory is tight, I would prefer the token bucket (O(1) per key) or a sliding-window counter approximation.

If several server processes on the same machine enforced the same limits, this design would break. A `threading.Lock` and an in-memory dict only exist inside one process, so each process would keep its own independent limiter. A client could get up to N × `limit` requests through, and each process would report only partial statistics. To fix this, the state would have to be shared: either in shared memory protected by a cross-process lock, or in a local store such as Redis over a Unix socket. Another option is to route each `(client_id, endpoint)` to the same process every time (for example, by hashing the key), so that only one process owns each key's state.

## 2. Scaling out: multi-instance deployment with Redis

For a horizontally scaled deployment with many gateway instances, the limiter state has to move out of process memory and into a shared store. Redis is the natural choice. Each `(client_id, endpoint)` would map to a Redis key such as `rl:{client_id:endpoint}`. A local lock no longer works across machines, so atomicity would come from Lua scripts: Redis runs each script atomically, which makes the whole read-evaluate-update step a single operation.

For Policy A, each key would be a sorted set of accepted-request timestamps. The script would remove expired entries with `ZREMRANGEBYSCORE`, count the remaining ones with `ZCARD`, add the new request with `ZADD` only if it is accepted (using a unique member per request), read the oldest score to compute `reset_after_ms`, and set `PEXPIRE` equal to the window so idle keys disappear automatically. For Policy B, each key would be a hash storing `tokens` and `last_refill`, and the refill, decision and consumption would all happen inside the script, again with an expiry. Different servers' clocks can drift apart, so the script should use Redis's own time (`TIME`) instead of each instance's clock. Statistics could be kept with atomic `INCR` counters, and active keys could be tracked with a set or a HyperLogLog.

At larger scale, Redis Cluster can spread keys across nodes. Hash tags keep all the keys used by one script in the same slot. The main new costs are a network round-trip on every request and a new dependency that can fail. Latency can be reduced by letting each instance lease a small batch of tokens and spend them locally, which trades a little accuracy for speed. If Redis is unavailable, the system needs a clear policy: fail open (allow requests, so the gateway stays available) or fail closed (reject them, protecting the backend). That policy should sit alongside a circuit breaker and possibly a local fallback limiter set to roughly `limit / N` per instance. Reads and writes should go to the primary so that replication lag does not cause stale decisions. Memcached could also be used with compare-and-swap retry loops, but it has no server-side scripting and handles contention poorly, so Redis is the better fit.
